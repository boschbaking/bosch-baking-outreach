01

Architecture

A single Next.js 16 application (App Router, TypeScript, Tailwind) handles both the UI and the backend — every write goes through a Route Handler under /api/*, which talks to Supabase and, for drafting, the Claude API. There's no separate backend service to keep in sync.

  • Frontend — Next.js App Router. Server Components fetch and render prospect/draft data directly from Supabase (no client-side data-fetching layer to maintain); interactive pieces (editing, drag-and-drop, filters) are small Client Components layered on top.
  • Backend — Next.js Route Handlers under app/api/. Each one authenticates the request via the Supabase session cookie, then reads or writes through Supabase's row-level security — there's no separate service-role admin key to protect.
  • Database & auth — Supabase (Postgres + built-in auth). Sign-in is passwordless email links, so there's no password to store or leak.
  • AI — Claude API, called from one module (lib/ai/). Drafting logic, quality checks, and the voice rules all live there, isolated from the routes that call them — swapping models or providers later is a change in one place.
  • Email sending (Phase 3, not yet wired) — planned around Resend, behind the same kind of provider-agnostic module as the AI layer. See §06.
Why this shape: a wholesale bakery's outreach tool doesn't need microservices — it needs one system Brandon can trust, that's cheap to run, and where "swap the AI provider" or "swap the email provider" is a single-file change rather than a rewrite.

04

User flow

  1. Get prospects in. Import a CSV or add one by hand. Duplicates (by email) and anything on your suppression list are skipped automatically.
  2. Research. On a prospect's page, jot down what you actually know — menu type, whether they do banquets, current bread supplier, whatever's real. Leave the rest blank; nothing gets guessed.
  3. Draft. Pick a campaign mode (New Prospect / Lost Customer / Dormant / Existing Upsell) and generate. Claude writes from your research notes and your voice rules, and a fast rule-based check scores it before it ever reaches you.
  4. Approve. Every draft lands in the Approval Queue. You preview, edit inline, approve, reject, or ask for a regenerate with feedback — alone or in bulk, filtered by city, business type, or campaign.
  5. Track. Approved prospects move to the pipeline. Drag a card as things happen — replies, sample requests, closed accounts.
Steps 1–4 above are live today. Sending, follow-ups, and reply tracking (the rest of the loop) are Phase 3 — see §07 for exactly where the line sits.
05

Security considerations

  • No service-role key in the app. Every query runs as the signed-in user through Postgres row-level security, not a privileged admin key — there's nothing catastrophic to leak from an env var.
  • Passwordless auth. Magic-link sign-in means there's no password database to breach, and no reused-password risk.
  • Secrets stay server-side. The Anthropic API key never reaches the browser — it's read only inside Route Handlers.
  • Suppression is enforced at the API, not just the UI. Both the CSV importer and the manual "add prospect" endpoint reject emails/domains on the suppression list before they can be created — so it can't be bypassed by skipping a particular screen.
  • Do Not Contact blocks drafting. The draft-generation endpoint refuses to run for a prospect flagged DNC, not just the send step later.
  • Every write is logged. activity_log records who changed what — useful both for your own memory and for catching anything that looks wrong.
  • Environment variables, not hardcoded values. Supabase and Anthropic credentials are read from env vars everywhere; .env.local is git-ignored.
06

Email sending approach (Phase 3)

Not wired up yet — Phase 1 stops at Approved. The schema and the module boundary are already in place so this is additive, not a rewrite:

  • Provider: Resend, called from one module (mirroring lib/ai/) so switching providers later touches one file.
  • Modes: Manual (draft only, you send), Assisted (you approve batches, system paces the sends), Trusted (approved campaign rules send within limits) — the sending_mode column on campaigns already models this.
  • Pacing: sending_settings already holds max daily sends, weekday-only, sending window, and min/max spacing between sends — a background job just needs to read it and act.
  • Follow-ups: follow_up_sequences stores wait-N-business-days steps per campaign; a reply, or a status of Not Interested / Customer / Do Not Contact, halts the sequence.
  • Replies: inbound parsing (via Resend's webhook or an inbox integration) writes to replies, gets classified, and drafts a suggested reply — which, like everything else here, you approve before it goes out.

Everything above Phase 1's line in the original spec — automated web research, AI-assisted rewrite loops, the Voice Training screen, the Campaign Builder UI, and all of Phase 3 — is deliberately not built yet, though the schema already has a home for each of them.

08

Recommendations

  • Automated web research (Phase 2) will need either a search API (Claude with web search, or a dedicated one) or you'll keep filling in research notes by hand — both are fine, but worth deciding before that phase starts, since it affects cost per prospect.
  • Voice Training UI — the voice_examples and voice_settings tables exist and drafting already reads from them, but there's no screen yet to paste in examples or edit banned phrases — right now that's a direct database edit. Worth prioritizing early in Phase 2 since it directly improves draft quality.
  • Reply ingestion needs a decision on how replies actually reach the system — a Resend inbound webhook, forwarding to a dedicated address, or an IMAP poll of your real inbox. Each has different setup cost; happy to lay out the trade-offs when Phase 3 starts.
  • Team access — right now any signed-in user has full access to everything (reasonable for one person). If anyone besides you ever needs a login, worth revisiting whether they should see every prospect or just their own.
